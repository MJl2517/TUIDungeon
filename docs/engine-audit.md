# Аудит движка и план оптимизации

Этот документ описывает состояние **до исправлений**. Результаты первого этапа
и новые контракты приведены в [отчёте об оптимизации](optimization.md).

Дата: 8 октября 2026. Проверена текущая рабочая копия, включая незакоммиченные изменения.
Игровая логика и авторские карты в рамках аудита не изменялись.

## Вывод

JSON подходит для исходников контента. Основная подтверждённая проблема производительности —
повторные расчёты видимости, обработка всей карты вместо видимой области и создание/сериализация
полного изображения. Замена JSON на SQLite или бинарный формат сама по себе эти операции не ускорит.

Проект — рабочий расширяемый прототип. Новые варианты предметов, монстров и испытаний уже можно
создавать данными. Для большого мира и дальнейшего развития механик нужны более строгая граница
между шаблонами и состоянием, пространственные индексы, единая подготовка кадра и контракт команд.
Переписывать проект с нуля или вводить полноценный ECS сейчас оснований нет.

## Проверка и измерения

189 существующих unittest прошли, включая API и псевдотерминал. В ограниченной среде первый запуск
остановлен после зависания на API-тесте; полный повтор выполнен с разрешением на запуск вне sandbox.
Отдельные диагностические пробы обнаружили три дефекта, не покрытых существующей проверкой.
Графический браузерный прогон в этом аудите не выполнялся.

Новый воспроизводимый инструмент:

```bash
.venv/bin/python -m scripts.benchmark_engine --sizes 32 100 256 --repeat 3
.venv/bin/python -m scripts.probe_engine_contracts
```

Windows: вместо `.venv/bin/python` использовать `.venv\Scripts\python.exe`.
Оба инструмента создают карты только в памяти, не сохраняют документы в packs.
Второй возвращает код 1, пока хотя бы один из трёх проверяемых контрактов нарушен.
Это диагностический сценарий, а не тест, закрепляющий ошибочное поведение как норму.

Измерения: Python 3.13.5, Linux x86-64, Intel Core i7-2600. Медиана трёх повторов после прогрева,
сборка мусора разрешена. Основной повтор сделан после завершения тестов. Это ориентир на данной
машине, не гарантия FPS и не оценка p95. Сырые результаты: [engine-baseline.json](benchmarks/engine-baseline.json).

| Сценарий | Разбор JSON | Один расчёт света | Подготовка browser snapshot |
| --- | ---: | ---: | ---: |
| Открытая яркая карта 32×32 | 0,17 мс | 5,50 мс | 17,17 мс |
| Открытая яркая карта 100×100 | 1,16 мс | 138,40 мс | 437,16 мс |
| Открытая яркая карта 256×256 | 7,58 мс | 2222,32 мс | 6997,61 мс |
| 100×100, 1000 предметов | 1,92 мс | 134,41 мс | 431,56 мс |
| 100×100, тьма, 100 источников радиуса 6 | 1,24 мс | 150,92 мс | 477,22 мс |
| 100×100, тьма без источников | 1,21 мс | 0,39 мс | 41,16 мс |

Это синтетические карты без стен: особенно тяжёлый случай для текущего алгоритма лучей.
Текущая авторская `base:crypt` 100×100 отдельно дала **48,31 мс** на snapshot и **1,31 мс** на свет.
Расположение стен и источников радикально меняет результат. Нельзя переносить цифру 7 секунд
на любую карту 256×256. Небольшая разница между сценариями с 0 и 1000 предметов — шум измерения,
а не ускорение от добавления предметов. AI в сценариях отсутствует.

Разбор JSON измерен из строки в памяти, без дискового чтения и проверки схемы.
Проверка схемы отдельно: 1,35 мс для 100×100 и 7,86 мс для 256×256.
Snapshot включает подготовку изображения и словарей, но не HTTP, браузер и JSON-кодирование.
Кодирование отдельно: 6,18 мс / 39,91 мс; полный ответ — примерно 552 КБ / 3,61 МБ.

Чистая команда ожидания: 0,054 мс без предметов и 0,494 мс с 1000 предметами.
Пара шагов восток/запад: 0,095 / 0,896 мс. Линейные обходы заметны, но сейчас не доминируют.
Загрузка/проверка всех 718 документов на прогретой файловой системе: 179,88 мс;
построение runtime-каталога: 16,06 мс. Холодный диск отдельно не измерялся.

Профиль snapshot открытой карты 100×100: три вызова `LightField.calculate`, 30 000 вызовов
`line_of_sight`; около 95% времени под профилировщиком ушло в расчёты света.
В обычном кадре TUI счётчик вызовов показал четыре расчёта света.

## Подтверждённые дефекты

1. **Предмет, размещённый кистью, остаётся нарисованным после подбора.**
   [mapTools.ts](../studio/src/mapTools.ts) записывает одновременно тайл и экземпляр предмета.
   [map_cells](../tuidungeon/presentation/art.py) запекает рисунок тайла в основу уровня.
   `Engine.pickup_item` удаляет экземпляр, но основа остаётся. Воспроизведение: поставить
   `base:decor_dagger`, подобрать, отойти. Предметов на земле уже 0, а на клетке всё ещё `†`
   и описание «Кинжал». Исправление: кисть должна размещать отдельно основание и объект;
   движок рисует объект только из живого экземпляра. Нужна миграция уже нарисованных рецептов,
   сохраняющая авторские исходники. Просто стирать клетку после подбора неправильно: потеряется фон.

2. **Неизменяемость шаблонов поверхностная.**
   [StrictModel](../tuidungeon/content/schemas.py) запрещает присвоение полей, но вложенные списки
   остаются изменяемыми. [TestSession](../tuidungeon/tooling/sessions.py) копирует словарь документов
   поверхностно. Изменение `store.get(...).walkability[y][x]` попадает в обе запущенные сессии;
   при этом `DungeonMap.rows` уже построена и сохраняет старую проходимость.
   Это нарушение контракта для Python-расширений, не доказательство того, что обычное сохранение
   через Studio меняет активную сессию: `reload()` создаёт новые документы.
   Исправление: глубоко неизменяемые скомпилированные определения; временно — глубокий snapshot
   на границе сессии. Одно лишь добавление `frozen=True` проблему не решит.

3. **Преобразователь ссылок меняет произвольный текст.**
   [PackStore.runtime_catalog](../tuidungeon/content/packs.py) обходит все строки и удаляет
   `base:` у любой строки, похожей на ссылку. У предмета с описанием `base:secret` runtime-описание
   становится `secret`. Аналогичный риск есть у строковых параметров расширений.
   Исправление: преобразовывать только типизированные поля ссылок; затем перейти к одному
   каноническому виду `pack:id`, убрав необходимость такого преобразования.

Первый дефект виден обычному игроку. Второй важен для безопасного расширения Python-кода.
Третий проявляется на специальном, но допустимом содержимом. Эти дефекты воспроизводятся
`scripts.probe_engine_contracts`, исправления в рамках аудита не внесены.

## Узкие места и ограничения архитектуры

- **Повторная видимость и полный кадр.** `Engine.lighting` каждый раз вычисляет новое поле.
  `TestSession._snapshot` вызывает его через render, напрямую и через nearby_points.
  TUI отдельно вызывает `render` и `draw_colors`; последний снова строит изображение и освещение.
  `TerminalKeyboard` имеет timeout 100 мс, а цикл перерисовывает экран и при пустом вводе.
  Карта может нагружать CPU даже когда игрок ничего не делает.
- **Дорогой алгоритм на открытых пространствах.** В [lighting.py](../tuidungeon/world/lighting.py)
  видимость проверяется отдельным лучом для каждой освещённой клетки всей карты. На открытой
  квадратной карте со стороной S это порядка O(S³), плюс расчёты источников света.
  Ограничивать дальность обзора только ради ускорения нельзя без изменения игровых правил.
- **Нет пространственных индексов.** Ход перебирает монстров и ловушки, nearby — все точки,
  pickup — все предметы. `_advance` и очистка сгоревших факелов обходят предметы всех посещённых
  уровней. Будущая большая кампания будет замедляться даже из-за вещей на других картах.
- **Повторное создание клеток.** `LightField.shade` создаёт Pydantic Cell для каждой тёмной клетки
  каждый кадр; `Level.render_cells` копирует всю сетку. Поэтому даже полностью тёмная карта
  100×100 требует примерно 41 мс на snapshot при почти бесплатном освещении.
- **Контент перечитывается целиком в редакторе.** `/api/library`, `/api/assets`, открытие документа
  вызывают reload; библиотека опрашивается каждые 5 секунд. Save также делает полные reload и
  проверку ссылок. `usages` каждый раз обходит все документы. Это не чтение JSON на каждом игровом
  ходе, а отдельная проблема роста библиотеки Studio.
- **Связь слоёв ещё неполная.** Level хранит PackStore и обращается к нему при отрисовке;
  application импортирует presentation.art; World использует авторские Pydantic Cell.
  В Level несколько полей типа `object` и нет строгого интерфейса запросов мира.
  Новая сессия/первый переход снова строят runtime-каталог. Типизированный compiler/repository
  уберёт это сцепление без отказа от существующих domain/application/world.
- **Реестр эффектов расширяем, реестр типов действий — частично.** Новый эффект получает параметры
  через MechanicsRegistry. Новый вид действия дополнительно требует изменения Literal в схеме,
  ACTION_KINDS и фабрики обработчиков. Описания и формы действий стоит также выводить из реестра.
- **Две системы определений.** Pydantic-документы адаптируются в domain dataclass через приватный
  `_parse`; отдельно существует legacy `content/data`. Нужен один авторский источник packs и явный
  компилятор, иначе новое поле приходится сопровождать в нескольких местах.
- **Сохранения жёстко связаны с картой.** SaveRepository записывает полное определение и rows
  каждого посещённого уровня; любое отличие определения при загрузке отвергается. Это осознанная
  текущая защита, а не случайная порча save. Но изменение описания/графики тоже блокирует загрузку,
  а изменения других шаблонов не имеют такой же полной проверки совместимости. Нужна политика
  версий контента, миграций и идентичности размещений.
- **История и холст Studio тоже масштабируются плохо.** Каждое движение кисти клонирует весь Doc,
  History держит до 100 полных копий и сравнивает JSON.stringify. Grid переразмеривает и рисует
  весь canvas. Например, 256×256 при zoom=1 и DPR=2 требует около 240 МиБ только для RGBA-пикселей
  одного полного canvas (расчёт, не замер памяти браузера). Нужны viewport и история изменений.
- **События хранятся без ограничения.** `Engine.events` растёт весь сеанс, хотя клиент получает
  последние 100. Для UI нужен ограниченный журнал; полноценный replay, если понадобится,
  должен храниться отдельно и иметь свой формат.

AI, боевой планировщик, механика голода и другие запланированные системы не считались багами
за отсутствие реализации. Текущий общий seed обеспечивает игровые броски, но UUID экземпляров
независимы: для сравнения replay следует нормализовать идентификаторы или выдавать их фабрикой.

## Способ хранения данных

| Данные | Рекомендуемое представление | Причина |
| --- | --- | --- |
| Авторские предметы, монстры, заклинания | JSON + строгая схема + стабильный `pack:id` | Формы Studio, Git diff, ручные правки и генерация агентом |
| Авторские карты | Пока текущий JSON; при росте palette + индексы и отдельные чанки | Меньше повторяющихся строк, локальные изменения и загрузка частей |
| Загруженные шаблоны | Общий неизменяемый ContentSnapshot | Один шаблон разделяют все экземпляры |
| Рабочая карта | Индексы тайлов, компактные маски, индексы объектов по клеткам | Нет разбора и поиска строк внутри каждого хода |
| Состояние сеанса | Экземпляры с ID, изменения объектов и ресурсов | Не смешивать HP/подобранный лут с авторскими файлами |
| Save небольшой игры | Версионированный JSON с состоянием и ссылками на ревизии | Простой, проверяемый и переносимый формат |
| Большая кампания | При подтверждённой необходимости SQLite для частичных транзакционных сохранений | Удобно обновлять уровни отдельно; не замена рабочей памяти |
| Сборка для игрока | При необходимости сжатый пакет/компилированный кеш | Производный артефакт, полностью восстанавливаемый из JSON |

Сейчас все 719 JSON-файлов, включая manifest, занимают около **899 КБ**. Рабочая crypt:
381 КБ с отступами, 167 КБ без отступов, около 2 КБ после zlib из-за множества повторов.
Это не обещание такого сжатия для любой карты, но явного дефицита диска пока нет.
Сжатие уменьшает файлы и доставку, а не число обходов объектов во время игры.

Для 256×256 массив 16-битных индексов тайлов занимает 128 КиБ, две маски по байту — ещё
128 КиБ. Это расчёт только этих буферов: определения, ссылки, runtime-объекты и графика
потребуют дополнительную память. `array('H')` и `bytearray` достаточно для первого варианта;
новые зависимости ради хранения сетки не обязательны. Битовые маски можно ввести позже.

## Целевая организация движка

```text
JSON packs -> проверка схем и ссылок -> ContentCompiler -> ContentSnapshot
                                                        |
                                                  SessionFactory
                                                        |
                       Command -> Engine -> RuntimeLevel + изменяемые сущности
                                     |
                              Result + события + revision
                                     |
                       FrameBuilder(viewport, revision)
                              /                 \
                           curses          browser API
```

Развивать существующие папки, а не переименовывать всё сразу:

- `content/compiler.py`: явное преобразование авторских документов, кеш по ревизии,
  таблица определений и индекс обратных ссылок. Проверка Pydantic на входной границе.
- `world/spatial.py`: `actors_by_cell`, `items_by_cell`, `traps_by_cell`, `points_by_cell`.
  Одна клетка может содержать несколько предметов/ловушек. Индексы обновляются через методы
  add/move/remove, восстанавливаются после загрузки; тесты сравнивают их с полным обходом.
- `world/lighting.py`: кеш статических источников и поля видимости. Отдельные ревизии
  непрозрачности, позиции наблюдателя и источников света. Применение кеша не должно сохранять
  старый свет после переноса/сгорания факела, перехода, загрузки или сброса сессии.
- `presentation/frame.py`: один снимок кадра для символов, цветов, осмотра и nearby;
  конструирование только запрошенной видимой области. Расчёт физического света остаётся
  доступен игровым проверкам вне viewport. Для browser — первый снимок и дальнейшие изменения
  клеток с revision и возможностью запросить полный снимок при рассинхронизации.
- `application/commands.py`: общий диспетчер типизированных команд для обоих клиентов.
  Проверка доступности и цели, изменение мира, расход ресурсов/времени, события.
  Получение списка доступных действий тоже должно приходить из application.
- Сервисы механик передают контекст мира через небольшой Protocol: запрос соседей, эффекты,
  изменение клетки, появление объекта. Стратегии/компоненты лучше растущей иерархии наследования.
  Пользовательский обработчик должен иметь определённое поведение при ошибке; ресурс не должен
  списываться наполовину. Полноценные транзакции всего мира вводить только под нужные операции.

## Порядок внедрения и критерии

1. **Зафиксировать корректность.** Превратить три диагностические пробы в regression-тесты
   при исправлении. Разделить основание и экземпляр предмета. Ввести истинную неизменяемость
   шаблонов и типизированные ссылки. Проверить две сессии, reset, save/load и внешнее обновление
   контента; исходные авторские файлы сохранять при миграции.
2. **Убрать лишнюю работу кадра.** Один расчёт поля на изменение мира, общий кадр TUI, отсутствие
   расчёта мира при пустом вводе, вкладке и мигании курсора. Начать с этого до смены алгоритма.
   Проверять счётчик вычислений, а не только плавающие миллисекунды.
3. **Улучшить видимость и viewport.** На открытых картах кеша недостаточно: каждый шаг меняет
   наблюдателя. Рассмотреть shadowcasting/интервальный обход видимости; сравнить на стенах,
   закрытых диагоналях, границах и нескольких источниках. Сохранить утверждённые правила
   видимости стен. Убрать Pydantic-валидацию и создание одинаковых чёрных Cell на каждом кадре.
4. **Индексировать мир и активные процессы.** Пространственные индексы и набор горящих источников.
   Для спящих уровней — абсолютное игровое время последнего обновления/истечения топлива,
   с согласованными событиями истечения. Не обходить всё снаряжение мира каждый ход.
5. **Ускорить Studio и поток контента.** Отслеживать изменённые файлы по stat + hash, проверять
   зависимые документы через обратный индекс. Хранить ревизии каталога, кешировать runtime-каталог.
   Undo/redo записывает одну команду мазка со старыми/новыми клетками; canvas ограничен viewport.
6. **Версии и большие миры.** Определить совместимость save и контента, затем добавить чанки,
   кеш сборки или SQLite, только если измерения загрузки/памяти/сохранения покажут необходимость.
   Нынешняя схема ограничивает сторону карты 256 клетками; увеличение лимита раньше оптимизаций
   усугубит задержки. Межкартовые переходы уже позволяют разбивать мир на уровни.

Предварительные бюджеты на этой же машине, которые предстоит подтвердить после реализации:
100×100 с 1000 предметами — чистая команда до 5 мс, подготовка кадра до 33 мс;
256×256 с viewport 80×24 — команда вместе с подготовкой кадра до 100 мс.
Нулевой ввод: 0 перерасчётов света. Это цели, а не уже достигнутые показатели.
Для будущего AI добавить самостоятельные сценарии 100/1000 существ: предметы их не заменяют.

## Рабочий процесс добавления возможностей

**Контракт → маленький сценарий → реализация → профилирование → данные через Studio.**
Для новой механики сначала определить параметры, допустимые цели, стоимость, события и
сохраняемое состояние. Затем маленькая тестовая карта и фиксированная последовательность
команд с seed; один обработчик в реестре, форма из схемы, один интеграционный тест для обоих
клиентов. Вариации уже существующей механики добавлять только JSON-данными.

Каждое изменение производительности сравнивать с сохранённым baseline на одинаковой машине.
Не ставить жёсткий общий таймер в unittest: в CI надёжнее проверять число расчётов, чтений,
инварианты индексов, отсутствие изменения шаблонов и детерминированность игровых результатов.
Медиану/p95, память и размеры ответов собирать отдельным benchmark-прогоном.
Текущий инструмент даёт медиану времени и размер ответа; память и p95 ещё нужно добавить.

Планируемый инструмент `content validate/build` должен проверять все пакеты, обратные ссылки,
миграции и контрольные суммы. Новый механизм нельзя считать готовым только потому, что его
параметры появились в форме: нужны применение, сохранение/загрузка и сброс тестовой сессии.
